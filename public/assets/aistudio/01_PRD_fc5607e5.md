# Liberty Cafe — Product Requirements Document (PRD)

**Document:** 01_PRD.md  
**Version:** 1.1  
**Status:** Planning baseline for Google AI Studio  
**Project:** Liberty Cafe

## 1. Product Overview

Liberty Cafe is a premium, responsive restaurant website with an online menu, three order modes, customer accounts, order tracking and a protected admin dashboard. The visual direction is the same reference discussed with the user: **Luxury Black & Gold**. The site will be built in Google AI Studio as React + TypeScript (Vite), prepared for Supabase, exported to GitHub and deployed to Cloudflare.

The website must support:
- **Home Delivery**
- **Takeaway / Pickup**
- **Dine-in**

The first build includes clearly labelled sample/demo menu products and demo content so the user can see the complete experience before entering the cafe's real products, prices, address, contact details and payment credentials.

## 2. Goals

1. Present Liberty Cafe as a premium, trustworthy cafe brand.
2. Let visitors browse menu categories and product details on desktop and mobile.
3. Let customers place delivery, takeaway and dine-in orders.
4. Give customers a clear order confirmation and status-tracking experience.
5. Give authorised staff/admin users tools to manage products, categories, orders, offers, delivery areas, tables and site information.
6. Keep frontend code Supabase-ready without creating a Supabase project or embedding secrets during the Google AI Studio build.
7. Prepare the app for GitHub export and Cloudflare Pages/Workers deployment.

## 3. Target Users and Roles

### 3.1 Visitor / Guest
- Browse active categories, available products, featured items and offers.
- Search and filter the menu.
- Add items to a cart.
- Place an order without creating an account, subject to checkout validation.
- View the order confirmation and track an order using its order number and the associated phone number or a secure tracking token.

### 3.2 Customer (signed in)
- All guest capabilities.
- Manage their profile and saved delivery addresses.
- View their own order history and order details.
- Submit reviews for eligible completed orders.

### 3.3 Admin
- Access the protected admin dashboard.
- Manage categories, products, prices, availability, variants/add-ons, banners, coupons, delivery zones and dine-in tables.
- View and update orders, verify manual payments, update order status and review customer feedback.
- Edit public cafe information, opening hours and payment instructions.
- View operational sales and order summaries.

**Security rule:** A visitor must never be able to select or self-assign the admin role during signup. New accounts receive the `customer` role. Admin access is granted only through a trusted Supabase-side process.

## 4. Scope and Features

### 4.1 Public Website
- Luxury homepage with hero banner, primary call-to-action, featured products, categories, best sellers, offers and contact/footer sections.
- About, Contact, Menu and Offers pages/sections.
- Responsive navigation, mobile menu and footer.
- Cafe phone, WhatsApp, address, social links and opening hours are configurable; do not invent or hardcode real business details.

### 4.2 Menu and Products
- Categories with image, name and display order.
- Product cards with image, name, short description, price and availability.
- Product detail view with full description, optional variant and add-ons, quantity and special instructions.
- Search by product name/description.
- Filter by category and availability; optional sort by price/popularity.
- Featured and best-seller flags.
- Admin can mark products unavailable without deleting them.
- Missing real images use a consistent local placeholder; do not use random external image URLs.

### 4.3 Cart and Checkout
- Add, remove and change item quantities.
- Display subtotal, eligible discount, delivery fee, tax (only if configured) and grand total.
- Persist a guest cart locally for the current browser; do not store payment secrets in browser storage.
- Validate prices, product availability, variants, add-ons, coupon eligibility and delivery fees on the trusted backend before creating an order.
- Collect customer name and phone for every order. Email is optional.
- Display clear validation, loading, success and failure states.

### 4.4 Order Modes

**Home Delivery**
- Customer selects or enters a delivery address, city/area and delivery notes.
- Address must match an active delivery zone.
- Show the applicable delivery fee and minimum order amount before order submission.
- Order status path: Pending → Confirmed → Preparing → Out for Delivery → Delivered (with cancellation where allowed).

**Takeaway / Pickup**
- Customer provides name and phone and may select a preferred pickup time.
- Show pickup instructions configured by admin.
- Order status path: Pending → Confirmed → Preparing → Ready → Completed.

**Dine-in**
- Customer chooses an active cafe table/table code from the admin-managed table list, or enters a table code if enabled by the admin.
- Customer provides name and phone.
- Order status path: Pending → Confirmed → Preparing → Ready → Completed.
- Table reservation is not part of the initial required scope; it may be added later as a separate feature.

### 4.5 Payment Options and Demo Behaviour
The initial interface may display these configurable methods:
- Cash on Delivery
- Cash at Cafe / Counter
- JazzCash (manual transfer)
- Easypaisa (manual transfer)
- Bank Transfer (manual transfer)
- Card / Online Payment **Demo Only**

Rules:
- Payment methods are controlled by admin settings and may be enabled/disabled individually.
- Cash methods remain unpaid until staff confirms receipt.
- Manual transfer methods show editable payment instructions and may accept a transaction reference and proof image. Their status remains `pending_verification` until admin verification.
- Card / online payment must be labelled **Demo Only — no real charge** until a real payment provider is selected and integrated. Do not simulate a successful real payment or claim money has been collected.
- Never store card numbers, CVV or other raw card data.

### 4.6 Customer Accounts
- Signup, login, logout and password reset using Supabase Auth.
- Guest checkout remains available.
- Customer profile, saved addresses, order history and review history.
- A customer can read only their own private account/order data.

### 4.7 Order Tracking
- Confirmation page shows order number, order mode, items, totals, payment status and next steps.
- Customer can view status updates for their own orders.
- Guest tracking must not reveal another customer's order using only a guessable order number; require an additional verification value or a random secure tracking token.
- Status history should show time-stamped progress events.

### 4.8 Admin Dashboard
- Overview cards: orders today, sales today, pending orders, products and customers.
- Order list with filters by date, mode, status and payment status.
- Order detail with customer contact, item snapshots, notes, payment information and status history.
- Product/category CRUD, image upload, prices, availability, featured/best-seller flags.
- Product variants and add-ons management.
- Coupon/offer management with dates and usage limits.
- Delivery zone and delivery fee management.
- Dine-in table management.
- Review moderation.
- Website settings: brand/contact data, address, opening hours, currency, tax, delivery/pickup settings and manual payment instructions.
- Analytics must use actual database data. Empty states are shown when there are no real orders; do not display fabricated sales figures in production.

## 5. Demo Content Requirements

Every product must have `is_demo = true`, a unique stable ID and slug, a category, a descriptive name, an illustrative PKR price, availability status, a sort order and a placeholder or supplied image path. Do not create just a handful of sample entries or lazy-load only a subset of the demo catalogue.

**Important:** All listed prices are illustrative demo prices in Pakistani rupees (PKR), not confirmed Liberty Cafe prices. They must be editable in the admin panel before launch. Ingredients, portion size and allergen information must be confirmed by the cafe before being shown as factual menu claims.

### 5.2 Product catalogue behaviour

- The public menu must expose all 150 active sample products, with search, category filters, price display and availability state. Use pagination, “Load more”, or virtualisation if needed, but do not silently omit products.
- Each category contains 10 demo products. Category counts must be computed from data, not hard-coded labels.
- Use the available local product/category placeholders until approved product photography is supplied. Do not invent remote image URLs or present unrelated images as actual product photos.
- Mark all seeded products as demo in the admin product list. The customer-facing storefront may show normal product cards without a distracting demo badge, but must not claim the sample prices are verified cafe prices.
- Demo products must be editable, markable unavailable and deletable through the protected admin product manager. Admins may delete a menu item after confirmation. Existing order-item snapshots must preserve the product name, description and price for historical receipts; the order_items.product_id reference may become null. The admin may also mark a product unavailable to keep it in the catalogue without accepting new orders.
- The initial seed must be idempotent: rerunning seed/setup must not create duplicate copies or overwrite products that an admin has already edited.

### 5.3 Other demo data

Sample coupon: `LIBERTY10` — 10% discount, demo only, with a minimum order and maximum discount configured in seed data. It must not be presented as a real campaign until approved.

Do not seed fake customer testimonials, fake delivered orders or fake revenue. Dashboard demo charts may use a separate clearly labelled preview state, but production analytics must never mix preview values with real data.

## 6. Business Rules

- Currency default: **PKR**. Currency and formatting must be configurable.
- Default timezone: `Asia/Karachi`, configurable through site settings.
- Real cafe address, city, phone, WhatsApp number, opening hours, tax rate, delivery zones and fees are **not yet provided**; leave them configurable and show sensible setup placeholders in admin. Do not invent them.
- Order totals are calculated and verified on the backend, never trusted from browser-submitted totals.
- Store product name, variant, add-on and price snapshots on each order item so historical orders remain correct if the live menu changes.
- Orders cannot be placed with unavailable products or inactive categories.
- Cancel rules and cutoff times should be configurable or handled by admin; do not silently cancel an order.
- Coupon rules must be validated server-side.
- Admin status changes must be recorded in order status history.
- Do not expose customer PII in public product/menu endpoints.

## 7. Non-Functional Requirements

- Mobile-first, responsive layout for phone, tablet and desktop.
- Accessible labels, keyboard navigation, visible focus states, adequate contrast and useful alt text.
- Fast initial load; lazy-load below-the-fold images.
- Clear loading, empty, success and error states.
- Secure role-based admin access enforced by Supabase RLS, not merely hidden UI.
- No Supabase service-role key, payment secret or private credential in frontend code or GitHub.
- Type-safe data models and reusable components.
- Reliable error handling when Supabase is not yet configured; show a setup state rather than crashing.

## 8. Out of Scope for Initial Build

- Live card acquiring/payment gateway, until the user selects a provider and supplies provider onboarding details.
- Automated JazzCash/Easypaisa settlement or bank reconciliation; manual transfer verification is sufficient initially.
- Table reservation/booking calendar.
- Multi-branch inventory and franchise management.
- Delivery rider live GPS tracking.
- AI chatbot, recommendation engine or generative AI features.
- Native iOS/Android apps.

## 9. Success Criteria

- All public pages and all three order modes work in responsive layouts.
- Demo menu can be browsed and edited through admin tools once backend is connected.
- Checkout creates an order only after backend validation.
- A customer cannot see another customer's account or order data.
- A non-admin cannot access or mutate admin data through direct requests.
- All demo payment methods are clearly distinguished from live payment processing.
- Project builds with `npm run build` and outputs to `dist` for Cloudflare.
