# Liberty Cafe — Technical Requirements Document (TRD)

**Document:** 02_TRD.md  
**Version:** 1.0  
**Status:** Planning baseline for Google AI Studio

## 1. Stack

- Website builder: Google AI Studio
- Frontend: React + TypeScript + Vite
- Routing: React Router
- Styling: CSS Modules or a consistent utility/CSS system; central design tokens
- Forms/validation: typed form handling with client validation; repeat all important validation on the backend
- Backend: Supabase PostgreSQL, Auth, Storage and Realtime where appropriate
- Source control: GitHub, created using AI Studio Export to GitHub
- Hosting: Cloudflare Workers & Pages connected to GitHub
- Package manager for deployment: npm; keep `package-lock.json`

Do not add Vercel to this workflow. Do not create the Supabase project/database inside Google AI Studio. AI Studio must generate a Supabase-ready frontend and backend integration layer only.

## 2. Architecture

### 2.1 Frontend layers

1. **Pages:** public pages, customer pages and protected admin pages.
2. **Components:** navigation, footer, product cards, category cards, cart, forms, status chips, dialogs and dashboard widgets.
3. **Domain/types:** TypeScript types that match `05_Backend_Schema.md` exactly.
4. **Services:** typed functions for auth, menu, cart/checkout, orders, reviews, admin and site settings.
5. **Supabase client:** one typed client initialized from environment variables.
6. **State:** local cart state persisted safely in browser storage; server state loaded from Supabase. Never treat browser totals as authoritative.

### 2.2 Backend boundary

- Public menu reads may use the Supabase anon/publishable key under restrictive RLS.
- Authenticated user reads/writes must be scoped to `auth.uid()`.
- Admin reads/writes must be authorised by RLS and the verified admin role.
- Order creation and price/discount/delivery calculations must use a trusted server/database function. Implement a secure `place_order` RPC or Supabase Edge Function. The browser sends product identifiers and quantities, not trusted totals.
- Payment proof handling must use private storage and owner/admin access policies.
- Never expose Supabase service-role credentials to React/browser code.

### 2.3 Data source of truth

Supabase is the source of truth for products, availability, category ordering, prices, delivery zones, coupons, orders, payments, reviews and site settings. The client may cache read-only menu data briefly, but must refresh/validate availability and prices before order placement.

## 4. Environment Variables

Create `.env.example` with names only and non-secret placeholders. Use Vite `VITE_` prefix for values intentionally exposed to the client:

| Variable | Required | Use |
|---|---|---|
| `VITE_SUPABASE_URL` | Yes after backend setup | Supabase project URL |
| `VITE_SUPABASE_ANON_KEY` or `VITE_SUPABASE_PUBLISHABLE_KEY` | Yes after backend setup | Public client key protected by RLS |
| `VITE_SITE_URL` | Recommended | Canonical public site URL |
| `VITE_ENABLE_DEMO_MENU_BADGE` | Optional | Enable a visible preview badge for demo menu data |

Do not add a service-role key to any `VITE_` variable. If an Edge Function or Cloudflare Worker requires a service secret, store it only in the server-side secret manager and document it separately; do not commit it to `.env.example` or GitHub.

Payment provider secrets are not required for this initial demo. Do not invent or request credentials during the AI Studio build.

## 5. Supabase Integration Requirements

- Add a single reusable Supabase client module, e.g. `src/lib/supabase.ts`.
- Read URL and public key from `import.meta.env`.
- Validate missing environment values and show a clear configuration message; do not crash or hardcode fake credentials.
- Keep SQL/schema planning in `05_Backend_Schema.md`; the AI Studio build must not claim that tables or an actual Supabase project already exist.
- Match table, column, enum and relationship names exactly with `05_Backend_Schema.md`.
- Use generated or carefully maintained TypeScript database types.
- Implement loading, empty, success and error states for all server-backed pages.
- Avoid broad unrestricted `.select('*')` calls for sensitive tables.
- Use Supabase Auth session handling and protected routes for customer/admin UX.
- UI guards are supplementary; RLS is the actual security boundary.

## 6. Auth and Permissions

- Supabase Auth email/password signup and login; phone is a customer contact field, not an assumed OTP login provider.
- Guest checkout remains supported.
- A trigger creates `profiles` with `role = 'customer'` for new users.
- Never accept `role` from the signup form or allow a user to update their own role.
- Admin promotion happens only in a trusted Supabase dashboard/SQL procedure.
- Use an `is_admin()` database helper or equivalent safe RLS strategy; avoid recursive profile-policy checks.
- Password reset uses Supabase Auth's supported redirect flow and configured allowed URLs.

## 7. Storage

Create the following buckets during the later Supabase setup:

| Bucket | Visibility | Purpose | Policy |
|---|---|---|---|
| `product-images` | Public read | Product photography | Admin-only upload/update/delete |
| `category-images` | Public read | Category artwork | Admin-only upload/update/delete |
| `banner-images` | Public read | Homepage/promotional banners | Admin-only upload/update/delete |
| `payment-proofs` | Private | Manual transfer receipt screenshots | Only the related order owner and admins can read; upload path/order ownership is validated |

Use unique object names, validate MIME type and file size, and avoid trusting file extensions. If avatars are added later, document a separate bucket and policy before implementation.

## 8. Backend Operations

Required operations/services:
- Public: list active categories, list available products, get product by slug, list active banners and active offers.
- Customer: manage own profile and addresses, create order through `place_order`, list own orders, read own order status history, upload/read own payment proof, submit eligible review.
- Admin: CRUD products/categories/variants/add-ons/coupons/delivery zones/tables/banners/site settings, manage orders and payments, moderate reviews, view analytics.

`place_order` must re-read product and option prices, confirm availability, validate selected order mode, validate coupon and delivery zone, calculate totals, write immutable item snapshots and create the order atomically. It must reject malformed, excessive or unavailable items. Do not accept client-submitted `grand_total` as authoritative.

For guest tracking, use an unguessable tracking token or a second verification value; never expose private order details from order number alone.

## 9. Security Requirements

- Enable RLS on every exposed table.
- Public users may read only active public catalogue/settings data.
- Customers can access only their own profile, addresses, orders, payments/proofs and reviews.
- Admin policies must be checked at database level.
- Guest order placement must be rate-limited and validated; use Cloudflare Turnstile or equivalent anti-abuse protection if spam becomes a concern.
- Do not store card data.
- Do not put service-role keys, passwords, payment secrets or private storage URLs in source code.
- Use safe error messages; never return stack traces or secrets to users.
- Validate image upload type and size.
- Keep database functions using a fixed safe `search_path` when running with elevated privileges; grant execute only to intended roles.

## 10. Build and Cloudflare Requirements

- `package.json` includes `build` script that runs the Vite production build.
- Build command: `npm run build`
- Output directory: `dist`
- Add `public/_redirects` with SPA fallback (`/* /index.html 200`) or an equivalent Cloudflare-compatible route fallback.
- Keep `package-lock.json`; do not retain `bun.lock` or `bun.lockb` in the final npm deployment repository.
- Root `.npmrc` must contain exactly: `legacy-peer-deps=true`.
- Include Node version guidance using a currently supported LTS release compatible with dependencies; record the exact version in `.nvmrc` or `engines` after dependency validation.
- Ensure nested React Router URLs load after refresh.
- All required `VITE_` variables must be set in Cloudflare before the production build/deployment.

## 11. Quality Requirements

- `npm run build` succeeds without TypeScript errors.
- No broken routes or missing component imports.
- No console errors in normal user flows.
- Responsive test widths: 360px, 768px, 1024px and 1440px.
- Test guest and signed-in checkout, all three order modes, demo payment selection, admin permissions and empty states.
- Do not claim Supabase is live until the actual project, schema, auth and policies are created and tested.
